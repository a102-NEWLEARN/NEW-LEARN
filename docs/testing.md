## 1. 자동 시험

커밋 전 훅과 CI 파이프라인이 **같은 포맷 · 린트 · 테스트 명령**을 돌립니다(CI 는 의존성 설치 · 빌드를 더 돌림). 순서는 시크릿 스캔 → 포맷 → 린트 → 테스트입니다. 커밋 훅과 MR 파이프라인은 바뀐 파일이 있는 영역만, dev 파이프라인은 모든 영역을 돌립니다. 명령은 [`.claude/stack.md`](../.claude/stack.md) 3절, 파이프라인은 [`.gitlab-ci.yml`](../.gitlab-ci.yml) 입니다.

| 영역 | 도구 | 시험 수 | 무엇을 지키나 |
|---|---|--:|---|
| Backend | JUnit · Testcontainers(로컬은 실제 PostgreSQL · Redis 컨테이너, CI 는 잡 옆에 띄운 PostgreSQL · Redis) · Spotless · Error Prone · NullAway | 514 | API 응답 · 오류 코드, 쿼리 결과, AI 결과 저장 전 검사. null 위험과 컴파일 경고는 빌드 실패 |
| Frontend | Vitest · ESLint · Prettier · 타입 검사(CI 빌드) | 640 | 화면 컴포넌트 · 상태 · 문구, API 호출 · 라우팅 |
| AI 워커 | pytest · ruff | 204 | 핵심 정보 추출(EXTRACT) 전처리 · 출력 검사 · 발생 시점 풀이, GMS 호출 재시도 · 시간 제한, 작업 큐 처리 · 결과 보내기, 임베딩 입력 · 벡터 검사 |
| Infra | `terraform test`(보안 그룹 · 백업 버킷), unittest([`infra/ci/`](../infra/ci/) 시험 파일 14개 — 배포 태그 MR · 뉴스 수집 · 분야 라벨 · AI 결과 적재 변환 · 부하 시험 도구 · 지난 기사 B2 변환, 그리고 8절 정확도 평가 도구 일곱), promtool(경보 규칙) | 425 | 인프라 코드와 운영 스크립트, 8절 정확도 평가 도구 |
| 하네스 | 셸 시험([`.claude/hooks/tests/`](../.claude/hooks/tests/)) | — | 커밋 훅 · 시크릿 스캔 · MR 규칙 검사 자체 |

- 시험 수는 dev 에서 시험 함수를 센 값입니다 — Backend 는 `@Test` · `@ParameterizedTest`, Frontend 는 `it(` · `test(` · `test.each`, AI 는 `def test_` · `async def test_`. 매개변수로 여러 번 도는 경우는 한 번으로 셌습니다. Backend 는 2026-11-16(Jira 224 반영), AI · Infra 는 2026-11-15, Frontend 는 2026-11-13 에 센 값입니다. Infra 만 함수를 세지 않고 `unittest discover` 가 실제로 돈 수입니다
- MR · dev 파이프라인마다 `w0:rules` 가 저장소 전체와 MR 커밋 이력에서 시크릿을 한 번 더 찾고, MR 이면 커밋 제목 · MR 제목 규칙을 봅니다. MR 본문 양식은 기계가 보지 않습니다
- dev 를 분야 브랜치(`infra` · `backend` · `frontend` · `ai`)에 맞추는 MR 은 dev 에서 이미 검사한 커밋이라 무거운 잡을 다시 돌지 않습니다. 배포 태그 MR(`deploy/app` · `deploy/ai`)을 머지한 dev 커밋도 태그 한 줄만 바뀌어 영역 검사를 다시 돌지 않습니다(`w0:rules` · `w12:infra` 는 돈다)
- **머지 막기(Pipelines must succeed)는 켜지 않았습니다**(`SSOT.md` 6절). 파이프라인이 성공한 뒤에 머지하는 것은 팀 약속이고, 커밋 훅은 클론마다 설치해야 돌아갑니다

### 화면 첫 로딩 — Lighthouse (2026-11-16)

프론트 첫 화면은 Lighthouse 로 잽니다 — 브라우저가 페이지를 불러 점수(성능 · 접근성 · 권장사항 · SEO)와 로딩 지표를 내는 도구입니다. 운영 사이트의 손님 화면 5개(랜딩 · 로그인 · 홈 · 이슈 · 기사)를 모바일 기본 조건(느린 4G · CPU 4배 느림을 흉내 낸 시뮬레이션, 캐시 없음)으로 3번씩 재 가운데 값을 씁니다. CI 에서 돌지 않고 손으로 잽니다(Jira S15P31A102-218).

| 무엇을 바꿨나 | 아침 운영 → 배포 뒤 운영 (5화면) | 근거 |
|---|---|---|
| `robots.txt` 를 둠 · 사용 분석 스크립트 `defer` · nginx 응답 문자셋 `utf-8` | SEO 92 → 100, 권장사항 69 → 73, 성능 +1 ~ +8(랜딩 50 → 58), TBT 랜딩 694 → 438ms, 실제 LCP 모두 줄어듦(기사 0.99 → 0.89초) | [`SSOT.md`](../SSOT.md) 10절 2026-11-16 두 줄 |

- **TBT** 는 JS 때문에 입력을 못 받은 시간, **LCP** 는 화면에서 가장 큰 내용이 뜬 때입니다. 실제 LCP 는 느린 조건 없이 Chrome 이 그대로 그린 때(`observedLargestContentfulPaint`)이고, 시뮬레이션 LCP 는 Lighthouse 가 느린 조건으로 다시 계산한 값입니다
- **시뮬레이션 LCP 는 늘었습니다**(랜딩 8.3 → 9.1 · 이슈 6.8 → 7.4 · 기사 6.8 → 7.7초). `defer` 로 `analytics.js` 요청 우선순위가 High → Low 가 되어, Lighthouse 계산 속에서 Google 태그(179KB)가 늦게 시작하고 LCP 도 그만큼 늦게 나옵니다. 같은 측정 기록에서 우선순위만 High 로 고쳐 다시 계산하면 랜딩이 8.97 → 7.52초로 줄고 실제 LCP 는 1.61초 그대로입니다(`lighthouse -G` 로 기록을 받고 `-A` 로 계산)
- **재 보고 계획을 바꿨습니다.** 처음 계획은 화면 단위 코드 분할이었는데, 번들을 source map 으로 나눠 보니 빠질 몫이 우리 번들의 약 14%(원본 약 125KB)였습니다. 받는 JS 491KB 중 205KB 가 사용 분석 스크립트였고, 랜딩은 애니메이션 때문에 스크립트 실행이 8.3초(로그인 0.2초)였습니다
- 🔴 **이슈 · 기사 CLS(0.054 · 0.098)는 못 고쳤습니다.** CLS 는 불러오는 동안 화면이 밀린 정도입니다. Lighthouse 는 헤더 로고를 짚었지만 크기를 적어도 그대로였고, Chrome layout-shift 기록으로 보니 로딩 자리(Skeleton)보다 큰 제목 · 요약이 들어오며 아래가 61 ~ 95px 밀립니다(Jira S15P31A102-222)
- 🔴 **실험실 값입니다.** 느린 폰 · 느린 망에서 직접 잰 전후 비교는 없습니다. SEO 100 은 Lighthouse 기본 점검 항목의 점수라 검색에 나온다는 뜻이 아닙니다. 원본 보고서는 작업자 PC 에만 있습니다

## 3. 단계 부하 시험

입구 로그 7일로 뽑은 실제 요청 비율 그대로, 운영 사이트에 동시 요청을 1 · 2 · 4 · 8 … 로 1분마다 두 배씩 올립니다(상한 128). 따로 도는 감시 스레드가 p95 · 5xx · health 를 보다 기준을 넘으면 스스로 멈춰 운영을 지킵니다. 부하를 보내는 서버의 CPU 도 함께 봅니다 — 잰 값이 보내는 쪽 한계에 묶이지 않게 하려는 기준입니다.

| 언제 | 포화 처리량 | 먼저 막힌 곳 | 근거 |
|---|---|---|---|
| 2026-11-12 첫 시험 | 초당 약 90건(최대 93.1), 오류 0 | DB CPU | [`load-results.md`](../infra/server/perf/load-results.md) |
| 2026-11-13 고치기 전 다시 잼 → 고친 뒤 | 초당 93.0 → 123.3건(약 32%), 동시 4 p95 99.6 → 74.4ms | 그대로 DB CPU | [`results-194.md`](../infra/server/perf/results-194.md) |

- 측정 조건: 15분 수집 · 자동 분석이 꺼진 때, 워커 서버 CPU 크레딧이 남아 있을 때, 단계마다 한 번. 두 시험 모두 동시 32 에서 멈췄습니다. 사람 수(동시 접속자)로 바꾸어 말하지 않습니다
- 🔴 **지금 조건과 다릅니다.** 2026-11-13 부터 15분 수집과 자동 분석이 켜져 있어 분석 결과 저장 · 판정 후보 검색이 같은 DB 를 씁니다. 그 상태의 포화 처리량은 다시 재지 않았습니다
- 부하를 보내는 관리 서버에서 CI 잡이 돌면 보내는 쪽 CPU 기준에 걸려 멈춥니다. 재기 전에 러너 잡이 없는지 봅니다([`perf/README.md`](../infra/server/perf/README.md) 「피할 때」)

## 4. 무중단 배포 확인

새 Pod 를 먼저 띄우고 준비 확인을 통과한 뒤 옛 Pod 를 끝내도록 설정했습니다([`SSOT.md`](../SSOT.md) 6절 「무중단 배포 조건」). 실제 교체 동안 관리자 PC 에서 사이트 health 를 계속 불러 이를 확인했습니다.

## 5. 데이터 적재와 쿼리 교체 검증

- **운영에 넣기 전 리허설 두 번** — 관리자 PC 의 일회용 DB(R1)와 서버의 일회용 DB(R2)에서 같은 명령으로 먼저 돌립니다([`infra/server/data-load.md`](../infra/server/data-load.md))
- **운영 적재는 한 트랜잭션으로** — 백업 → 끝이 `rollback;` 인 실행으로 넣을 수 · 바뀔 수를 먼저 보고 → 같은 명령의 `commit;`. 적재 SQL 은 첫 단계에서 DB 마이그레이션 버전을 검사해 맞지 않으면 멈춥니다
- **바꾼 목록 쿼리는 결과가 같은지부터** — 이슈 목록 SQL 을 바꿀 때 운영 데이터(읽기만)와 로컬에서 정렬 · 분야 · 쪽 크기 조합의 모든 쪽(472쪽)을 옛 · 새 SQL 로 비교해 다른 쪽 0 을 확인한 뒤 넣었습니다(2026-11-12 데이터, [`docs/plans/2026-11-12-issue-list-query.md`](plans/2026-11-12-issue-list-query.md), 비교 SQL [`list-equal.sql`](../infra/server/perf/list-equal.sql))
- **영향 범위는 공개 여부와 상관없이 전체 표로 셉니다** — 마이그레이션은 숨긴 기사까지 고칩니다. 2026-11-15 제목 앞 줄표를 떼는 V16 을 공개 기사 23,439건만 세고 만들었다가, 배포 직전 전체 165,255건을 세어 숨긴 기사의 「-4% 급락…」(음수 부호)도 떼어 버린다는 것을 찾았습니다. 운영은 V15 였고 V16 은 한 번도 돌지 않아 그 자리에서 고쳤습니다(!1029 → !1032). 이미 돈 마이그레이션이면 새 파일로 고칩니다
- **운영 데이터 손질도 같은 순서로** — 2026-11-15 잘못 붙은 기사-사건 쌍 1,656쌍을 뗄 때도 `rollback` 실행으로 손댈 수 · 남는 수를 먼저 보고 `commit` 했고, 뗀 행은 되돌리기 표에 남겼습니다([`infra/server/bigevent-detach.md`](../infra/server/bigevent-detach.md), `SSOT.md` 10절)

## 8. AI 가 묶은 사건 · 이슈 정확도

같은 사건끼리 묶였는지(F06 동일 사건 기사 클러스터링), 그 사건이 이슈 흐름에 맞게 붙었는지(F07 사건 중심 이슈 에볼루션 맵)를 **정답과 견줘 숫자로** 냅니다. 운영에서 읽기만으로 뽑은 목록을 Sonnet 이 전수 판정하고 그 위에 사람 판정을 덮어 정답을 만든 뒤, 운영 묶음과 비교합니다. 도구 · 절차 · 표 전부는 [`infra/server/eval/README.md`](../infra/server/eval/README.md), 원본 숫자는 [`SSOT.md`](../SSOT.md) 10절 2026-11-14 두 줄입니다(Jira S15P31A102-206).

| 무엇을 | 항목 | 쌍 F1 | B³ F1 |
|---|--:|--:|--:|
| 기사 → 사건 (운영 전체) | 18,637 | 0.754 [0.700, 0.798] | 0.880 |
| 사건 → 이슈 (운영 전체) | 3,176 | 0.841 [0.796, 0.888] | 0.942 |
| 기사 → 사건 (그날 실시간 워커가 묶은 몫) | 4,144 | 0.811 | 0.960 |
| 사건 → 이슈 (그날 실시간 워커가 만든 사건) | 2,215 | 0.822 | 0.951 |

- 실시간 몫은 적재분보다 **덜 뭉개고 더 쪼갭니다** — 기사 쌍 정밀 0.882 대 0.621, 재현 0.751 대 0.952. 둘을 합친 운영 전체는 적재분만 쟀을 때와 사실상 같습니다
- 🔴 **위 숫자는 2026-11-14 운영입니다.** 11-15 에 잘못 붙은 1,656쌍을 떼어 운영 묶음이 바뀌었지만 다시 재지 않았습니다 — 뗄 것을 바로 그 정답으로 골라서, 같은 정답으로 다시 재면 성적이 아닙니다(`SSOT.md` 10절 2026-11-15 두 줄)

- 지표는 **쌍**(같은 묶음에 든 쌍이 정답에서도 같은가) · **B³**(항목마다 내 묶음과 정답 묶음이 겹치는 정도) · 균질성 · 완전성 · V · ARI 입니다. 구간은 묶음 덩어리 단위 부트스트랩입니다. PRD 검증 목표 초안 SM-3 은 쌍 F1 · B³ F1 0.80 입니다
- 정답은 **사람 1명 + Sonnet** 입니다 — 판정 27,116건 가운데 사람이 200건(보정 50 · 검수 150)이고 나머지는 Sonnet 입니다. 사람이 겹쳐 본 검수 150건(적재분)에서 「기사가 그 사건에 맞다」가 0.858 [0.756, 0.922](층 가중), Sonnet 과 κ 0.666 입니다
- **틀리는 곳은 큰 사건입니다** — 사건에 모인 기사 수별 쌍 정밀도가 5~9건 0.886 → 50건 이상 0.466 으로 떨어집니다. 판정자를 바꿔 다시 판정해도 κ 0.955 라 판정 변덕이 아닙니다
- **화면에 보일 몫을 좁히면 이슈 쪽이 오릅니다** — 사건마다 공개 기사 3건 이상만 채점하면 이슈 쌍 정밀도 0.930 → 0.976 · F1 0.841 → 0.874 입니다(`clustering_eval.py metrics --min-articles 3`). 다만 재현율이 오르는 몫의 일부는 **경계에서 끊긴 정답 쌍**(기사 852 · 사건 2,361)이 분모에서 빠진 것이라 좁힌 값만 떼어 말하지 않습니다
- **말하지 못하는 것**: 사건에 묶이지 않은 기사는 위 표에서 재지 않습니다(아래 「대표 사건」이 그 몫 일부를 봅니다). 이슈 재현율은 위로 치우친 값입니다 — 같은 흐름으로 판정된 쌍을 모두 합치면 크게 내려갑니다(적재분에서 재 보니 0.758 → 0.211). 실시간 몫에는 사람이 겹쳐 본 표본이 없습니다. 자세한 것은 평가 README 와 `SSOT.md` 10절입니다

### 묶을 기사를 맞게 골랐나 — 대표 사건 (2026-11-15)

워커는 EXTRACT 에서 대표 사건(`primaryCoreIndex`)이 없다고 본 기사에는 판정을 아예 걸지 않습니다(`docs/api-internal.md` 3절). 운세 · 사설 · 단순 모집 안내처럼 사건이 아닌 기사를 거르려는 길인데, 여기서 틀리면 그 기사는 어떤 사건 · 이슈에도 못 들어갑니다. 위 표는 묶인 기사만 재므로 이 몫을 보지 못합니다.

최근 3일 기사에서 건너뛴 것 90건 · 고른 것 30건을 섞어 눈가림으로 판정했습니다.

| 층 | 결과 | 95% 구간 |
|---|--:|--:|
| 건너뛴 기사 중 사실은 사건이 있음 | 12/90 = 13.3% | 7.8 ~ 21.9% |
| 고른 기사 중 사실은 사건이 없음 | 1/30 = 3.3% | 0.6 ~ 16.7% |

모집단(그때 건너뛴 몫 32.1%)으로 다시 묶으면 **정밀도 0.967 · 재현율 0.939 · F1 0.953** 이고, 하루 약 138건(81 ~ 227)이 사건이 있는데 판정 줄에 들어가지 못합니다. 정답은 Sonnet 판정 120건(silver, 사람 검수 없음)이고, 도구 · 돌리는 법은 평가 README 2절, 원본은 `SSOT.md` 10절 2026-11-15 입니다.

- 🔴 **판정 기준은 운영 지시문을 그대로 씁니다**(`ai/app/extract/prompt.py` 의 대표 사건 대목). 처음엔 계약의 한 줄 요약(「운세 · 시세표 · 축사 · 해설」)으로 재서 13.3% 가 아니라 32.2% 가 나왔습니다 — 같은 120건 중 25건이 답이 갈렸고, 요약에는 「단순 모집 · 행사 · 이벤트 안내는 대표 사건이 아니다」가 빠져 있었습니다
- 「대표 사건 없음」 비율은 2026-11-12 까지 약 13% 에서 15분 수집을 켠 11-13 부터 약 32% 로 뛰었습니다. 그 까닭은 반만 찾았습니다 — 모집 · 행사 제목이 0.6% → 3.2% 로 늘었지만 그것만으로는 다 설명되지 않습니다

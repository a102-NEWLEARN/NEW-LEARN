# F02 카테고리별 뉴스·이슈 조회 — A13 통합 검색

상태: 확정 (2026-10-30, 사용자 승인)
이슈: Jira S15P31A102-43

계약 원본: [A13 통합 검색](../api-screen.md), [공통 규칙 · 오류 코드](../api.md) 1 · 2절, [데이터 모델](../data-model.md).
범위(제목만 · 부분 일치 · 1 ~ 50자 · 이슈에 묶인 사건만 · 공개된 기사만 · 유형마다 20개 · 최신순)는 2026-10-30 사용자가 골랐다.

## 목적

화면 검색창(Ctrl+K, 맥 ⌘K 빠른 이동)에 낱말을 치면, 제목에 그 낱말이 든 이슈 · 사건 · 기사를 유형별로 받아 그 화면으로 바로 간다.

## 이 티켓에서 하지 않는 것

- 요약 · 본문 · 사건 키워드(`label`) 검색, 낱말 나누기 · 형태소 · 오타 교정 · 비슷한 말, 맞는 정도로 줄 세우기
- 유형별 전체 개수 · 페이지 나누기 — 유형마다 20개에서 자른다
- 검색어 기록 · 인기 검색어 · 결과 저장(캐시)
- 검색용 인덱스(`pg_trgm`) — 기사가 늘어 느려지면 따로 한다
- 입구 요청 수 상한(A14 · A15 · A19 처럼 거는 것)
- 화면 변경 — 화면은 이미 이 응답 모양으로 부른다(frontend 브랜치 `frontend/src/api/search.ts`)

## 닿는 곳

- `GET /api/v1/search?q=` — 로그인 없이 연다(`SecurityConfig` 에 이미 열려 있음)
- 새 `search` 패키지: 컨트롤러 · 서비스 · 조회(유형마다 SQL 하나) · 응답 DTO. 기존 표(`issue` · `event` · `article`)를 읽기만 한다. 마이그레이션 없음

## 동작

1. 검색어 다듬기 — 앞뒤 공백을 지우고 NFC 로 맞춘다. 길이는 글자(코드포인트) 1 ~ 50. A19 용어사전과 같은 규칙이고, 오류 이유 문구는 검색에 맞춘다 — 「검색어를 입력해 주세요」 · 「검색어는 50자까지예요」(2026-10-30 사용자 — 검색창 안내가 「이슈, 사건, 기사 검색」이라 용어사전의 「찾을 단어」가 안 맞음). U+0000(NUL)이 든 검색어도 400 「검색어에 쓸 수 없는 글자가 들어 있어요」다 — PostgreSQL 이 이 글자를 받지 못해 전에는 500 이었다(2026-10-30)
2. 세 유형을 따로 찾는다. 제목에 검색어가 그대로 들어 있으면 맞다(대소문자 무시). 패턴 검색(`LIKE`)이 아니라 위치 찾기(`strpos(lower(제목), lower(검색어)) > 0`)라서 `%` · `_` · `\` 도 따로 처리하지 않고 그냥 글자다(2026-10-30 사용자 「따로 다루지 말자」 — `LIKE '%' || 검색어 || '%'` 에 그대로 넣으면 `%` 는 모든 제목, `_` 는 아무 한 글자, 끝의 `\` 는 닫는 `%` 를 글자로 만들어 결과가 조용히 틀어져서 함수를 바꿨다. 처음 계획에 적은 「`\` 로 500」은 틀렸다 — 패턴 자체가 `\` 로 끝날 때만 오류다(2026-10-30 reviewer 조수가 PostgreSQL 에서 확인))
   - 이슈: A2 목록에 나오는 이슈만(공개 기사가 있고, 보이는 사건이 문턱만큼 있는 것). 만든 때(`created_at`) 최신순
   - 사건: 이슈에 묶이고(`issue_id` 있음) 공개 기사가 있는 것만. 발생 시점(`occurred_at`) 최신순
   - 기사: 공개된 것만(`released_at` 있음). 발행 시각(`published_at`) 최신순
   - 시각이 같으면 id 가 큰 것 먼저. 유형마다 20개까지
3. 응답은 `{ issues: [{ id, title }], events: [{ id, title, issueId }], articles: [{ id, title }] }`. 없으면 빈 배열

## 데이터

저장하는 것은 없다. 읽는 칸은 `issue.title · created_at`, `event.title · issue_id · occurred_at`, `article.title · released_at · published_at` 이다.

## 성공 기준

- AC-1: 로그인 없이 부른다. 응답은 `issues` · `events` · `articles` 세 배열이고 항목 칸이 계약과 같다(사건은 `issueId` 포함). 결과가 없으면 200 과 빈 배열 셋이다. — 확인: `SearchApiIntegrationTest`
- AC-2: 제목에 검색어가 들어 있으면 나온다(부분 일치 · 대소문자 무시). 요약에만 있는 낱말로는 나오지 않는다. — 확인: `SearchApiIntegrationTest`
- AC-3: (뺌, 2026-10-30) 특수 글자를 따로 다루는 기준 — 위치 찾기라 지킬 규칙이 없다(동작 2)
- AC-4: `q` 가 없거나, 앞뒤 공백을 지운 뒤 비었거나, 50자를 넘으면 400 `VALIDATION_FAILED` 와 `errors[q]` 한국어 이유(동작 1 의 문구)를 준다. 50자는 받는다. 자모로 나뉘어(NFD) 온 한글도 같은 결과다. U+0000 이 들어 있어도 400 이다. — 확인: `SearchApiIntegrationTest`
- AC-5: 이슈에 묶이지 않은 사건과 공개 전 기사는 나오지 않는다. 공개 기사가 문턱보다 적은 사건과 그런 사건뿐인 이슈도 나오지 않는다(Jira 179 · 206). 보이는 사건이 `QUERY_MIN_PUBLIC_EVENTS` 개보다 적은 이슈는 **이슈 칸에서만** 빠진다 — 그 이슈의 사건은 사건 칸에 그대로 나오고, 눌러서 넘어가는 이슈 페이지도 살아 있다(Jira 208). 메인 흐름 사건이 없는 이슈(`QUERY_MIN_MAIN_EVENTS`)도 같은 방식으로 이슈 칸에서만 빠진다(Jira 224). — 확인: `SearchApiIntegrationTest` · `HiddenIssueEventApiIntegrationTest` · `MinPublicEventsApiIntegrationTest`
- AC-6: 유형마다 최신순(이슈 만든 때 · 사건 발생 시점 · 기사 발행 시각, 같으면 id 큰 것 먼저)으로 20개까지 준다. — 확인: `SearchApiIntegrationTest`(유형마다 21개, 20개 전체 순서. 이슈 `updated_at` 은 만든 때와 다른 순서, 같은 시각 10개를 섞어 넣음 — 정렬 기준이나 `id` 순서를 빼면 갈린다)
- AC-7: 한 번 부르면 SQL 은 세 번(유형마다 한 번)이다. — 확인: `SearchApiIntegrationTest`(기존 조회 시험의 쿼리 수 세기)
- AC-8: Swagger 에 「통합 검색」 태그 · `q` 설명 · 400 Problem 예시가 있다. 시험을 마친 뒤 `[확정] A13` 을 붙이고(`docs/backend-convention.md` 의 관례), 사이트에서 같은 모양인지 확인한다. — 확인: `OpenApiDocsTest` · 사이트 `/v3/api-docs`
- AC-9: 끝에서 끝까지 — 사이트 반영 뒤 `GET /api/v1/search?q=<낱말>` 이 200 과 세 배열, `q` 가 비면 400 이다. 지금 사이트는 기사 0건이라 빈 배열까지만 확인된다. 데이터가 생기면 결과가 나오는지 다시 본다. — 확인: 사이트 `curl`

시험: AC-1 · 2 · 4 · 5 · 6 · 7 은 `SearchApiIntegrationTest`(그 밖에 `%` · `_` · `\` 가 그냥 글자인지 한 번 더 본다), AC-8 은 `OpenApiDocsTest`. 검색어 규칙을 용어사전과 같이 쓰게 옮긴 것(`common/web/QueryText`)은 `DictionaryApiIntegrationTest` 가 그대로 본다. 깨진 쿼리 인코딩의 400 은 `QueryEncodingHttpTest`(실제 서버, cp949 바이트). `%ZZ` 는 자바 HTTP 클라이언트가 보내지 못해 로컬 서버에 curl 로 확인했다.

사이트 확인(AC-9, 2026-10-30, backend 7f6661b4): 「예산」 · 「%」 200 과 빈 배열 셋(사이트 기사 0건), 빈 `q` · `q` 없음 · 51자 400 과 검색 문구, Swagger `[확정] A13 통합 검색` · 태그 순서 카테고리 → 통합 검색, 용어사전 400 문구 그대로. 반영하는 동안 EC2 에서 1초마다 잰 health 900번(08:38:12 ~ 08:54:26, 교체 08:41:23 ~ 08:42:07 의 41번 포함) 모두 200, 최대 0.14초. 데이터가 생기면 결과가 나오는지 다시 본다.

## 상태별 동작

- 비었을 때: 200 과 빈 배열 셋. 화면은 「'낱말'에 맞는 이슈·사건·기사가 없어요」를 띄운다
- 처리 중: 해당 없음 — 한 번에 답하는 조회다
- 실패: DB 오류는 공통 500(`docs/api.md` 2절)
- 권한 없음: 해당 없음 — 로그인 없이 연다

## 엣지케이스

- 쿼리를 UTF-8 로 읽을 수 없으면(cp949 로 인코딩한 한글 `%B3%AA%B9%AB` · 깨진 퍼센트 `%ZZ`) 400 `VALIDATION_FAILED` 이고 `errors` 는 없다 — 쿼리 인자를 읽는 API 의 공통 처리다(`docs/api.md` 2절, 2026-10-30)
- 한 글자 검색(예 「물」)은 결과가 많다 — 유형마다 20개에서 자른다. 화면의 「N개 중 4개」는 20 을 넘어도 20 으로 보인다(2026-11-16 「4 / N개」에서 바꿨다, Jira 216)
- 제목이 같은 항목이 여럿이면 모두 준다(id 가 다르다)
- 검색어 안의 공백은 그대로 한 덩어리로 찾는다 — 「여야 협의」는 그 순서로 붙어 있어야 나온다

## 가정

- 기사 검색은 공개 기사 인덱스(V14 `article_public_published_idx`)를 최신순으로 훑으며 제목을 거른다 — 기사 표 전체(13만 행) 대신 공개 행만 본다(2026-11-11, Jira S15P31A102-190, 잰 값은 `infra/server/perf/results.md`). 결과가 20건이 안 되는 검색어는 공개 행을 끝까지 본다. 더 줄여야 하면 검색용 인덱스를 따로 한다. 그때 `pg_trgm` 인덱스는 `strpos` 를 돕지 않는다(돕는 것은 `LIKE` · `ILIKE` · 정규식) — 찾기를 `ILIKE` 로 바꾸고 `%` · `_` · `\` 를 이스케이프해야 하며, 특수 글자 시험이 그 변경을 지킨다. 또 trigram 은 세 글자 조각이라 한두 글자 검색어(「물」 · 「예산」)에는 인덱스가 범위를 좁히지 못한다(reviewer 조수가 2만 행으로 잼 — 「예산」은 2만 행을 다 읽고, 「예산안」은 20행)
- 이슈 · 사건은 공개 기사가 있는 것만 나온다(`docs/api.md` 1절, Jira 179)

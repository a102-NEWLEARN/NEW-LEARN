# 발표 전 단계 부하 시험 — 운영 사이트가 동시 요청을 몇까지 버티나 (2026-11-12)

## 무엇을 / 왜

발표(11-18) 날 운영 사이트가 동시 요청을 몇까지 버티는지 모른다. 지금까지 잰 것은 요청을 하나씩 차례로 보낸 시간(bench p50, 기사 목록 22ms)뿐이고, 저장소에 부하 시험 기록이 없다. 동시 요청을 1 → 2 → 4 → … → 128 로 단계마다 1분씩 올려 **포화 지점**(초당 처리 수가 더 안 늘고 지연이 꺾이는 곳)과 **먼저 막히는 층**(입구 Envoy · backend · DB · 워커 노드)을 한 번 잰다. 고치는 일은 결과를 보고 따로 정한다.

사용자 결정(11-12 08:2x): 막힐 때까지 올림(멈춤 조건에서 자동 정지) · 관리 서버 EC2 에서 보냄 · 시험 계정으로 회원 요청도 섞음 · **오늘 10:00 수집 전**에 돌림.

## 지금 구성에서 알아 둔 것 (조사 · reviewer 점검)

- 길: 도메인 → 워커(Lightsail xlarge, 4 vCPU 버스트형 · 계속 쓸 수 있는 CPU 약 1.6) → ufw(80/443 출발지 제한 없음) → Envoy 1대(hostPort) → backend 1대. EC2 에서 보낸 요청이 200 을 받은 기록이 있다(SSOT 10절)
- 입구 상한은 A14 가입 · A15 로그인 · A19 용어사전 · A26 문맥 뜻에만(IP 마다 1분). 공개 읽기 GET 에는 없다
- **로그인 잠김**: `LoginAttemptGuard` 는 비밀번호를 맞춰 보기 전에 시도를 예약하고 같은 아이디 6번째부터 1분 잠근다. 센 수는 성공해야 지워진다 → 같은 계정으로 동시에 로그인하면 잠긴다. 로그인 · 로그아웃 응답에서 CSRF 번호표(`XSRF-TOKEN`)가 바뀌고, 다음 요청의 `X-XSRF-TOKEN` 머리도 새 값이어야 한다(다르면 403). 로그아웃은 204. 세션 쿠키 `SESSION` 하루
- backend: 1대 · HPA 없음 · 메모리 상한 1Gi(힙 70%) · CPU 상한 없음 · Tomcat · Hikari(기본 10) · PG max_connections 기본값. **readiness** 는 DB 를 보고 timeout 1초 · 5초마다 · 2번 실패면 빠진다 → 풀이 밀리면 약 10초 안에 backend 1대가 빠져 전부 503. 공개 `/actuator/health` 도 DB 검사를 해서 같은 풀을 빌린다
- 관리 서버(EC2 t3.large, 2 vCPU, 크레딧 unlimited, **시간대 UTC**)에 Prometheus · Loki · Grafana · Alertmanager · CI 잡(잡 CPU 상한 1코어)이 같이 있다. tmux · Python 3.12 있음
- 지표: 노드 · 컨테이너 CPU · 메모리(30초), postgres_exporter, 입구 로그(Loki, 요청마다 `duration` · `user_agent` · `response_code`). backend JVM 지표(힙 · GC · 스레드)는 없다
- 시험으로 울 수 있는 경보: PodRestarting · ServiceDown · NewlearnLogsDropped · Alloy 메모리 → Mattermost 비공개 채널 「A102 배포알림」
- 화면은 전부 회원 전용(`frontend/src/routes.tsx` RequireMember). A2 · A3 · A6 · A7 · A8 은 회원이면 북마크 · 관심 여부를 더 읽는다
- 대시보드 「조회 성능」 · Jira 189 개선 후 값은 User-Agent `newlearn-bench.*` 를 뺀다 → 시험은 `newlearn-bench-load/1`. DB 통계 패널(표 단위 누적)은 섞이므로 시험 시각을 기록한다
- 10:00 매일 수집 전에는 수집 · AI 분석(B1 금지 중)이 돌지 않는다. Jira 152 다시 적재는 10:00 수집 뒤라 겹치지 않는다. 발표 날은 15분 수집이 켜져 있다는 차이를 결과에 적는다

- `infra/server/perf/load.py` (새) — 단계 부하 도구. 표준 라이브러리만(`http.client` · `threading` · `getpass`). `bench.py` 처럼 EC2 에서 돈다

  - 워커 넷 중 셋이 회원, 하나가 손님(발표 날 요청은 거의 회원, 손님 줄은 비교용). 결과는 회원 · 손님을 따로 낸다
  - **로그인은 한 명씩 차례로**, 측정 시간 밖에서: 단계에 새로 들어오는 회원 워커만 번호표 받기 → 로그인을 끝내고 다음 워커로. 세션은 단계를 넘어 유지한다. 번호표가 바뀌면 쿠키 · 머리를 같이 바꾼다. 로그인이 401 · 429 · 403 이면 바로 전체 정지(잠김 방지). 끝에 회원 워커마다 차례로 로그아웃(2xx 확인)
  - 비밀번호는 `getpass` 로 EC2 터미널에서만 받는다(채팅 · 명령 줄 · 기록에 안 남음). 예외 메시지 · JSON 에 요청 본문을 찍지 않는다. 아이디는 인자
  - 단계: 동시 1 · 2 · 4 · 8 · 16 · 32 · 64 · 128, 단계마다 60초, 앞 5초는 버림. 생각 시간 없이 계속 보낸다(닫힌 고리)

- 관리 서버에 Prometheus · Loki · CI 잡이 같이 있다 → EC2 CPU 70% 에서 멈춤(그러면 「보내는 쪽 한계」로 적음), 시작 전에 도는 CI 잡이 없는지 본다. 요청마다 Envoy 로그 한 줄이 Loki 로 가 로그 경보가 울 수 있다

## 되돌리는 법

- 시험은 상태를 남기지 않는다 — Ctrl-C 나 멈춤 조건이면 끝. 세션은 로그아웃으로 지운다(못 지운 것은 1일 뒤 만료)

- 문서 · 도구는 MR 되돌리기. 시험 계정은 남긴다(위 리스크)

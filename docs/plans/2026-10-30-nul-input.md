# 공개 입력의 NUL(U+0000) 을 500 대신 정해진 답으로 — A2 · A7 · A14 · A15 · A18 (Jira 43 후속)

## 무엇을 / 왜

PostgreSQL 은 글자 U+0000(NUL)을 받지 못해서, 이 글자가 든 값이 SQL 까지 가면 500 이 납니다. 오늘 A13 통합 검색(`GET /api/v1/search`) · A19 용어사전 `q` 는 막았습니다(!424).
2026-10-30 사이트에서 확인한 결과, 같은 500 이 아래 두 곳에서도 납니다.
- A2 이슈 목록 `GET /api/v1/issues?category=%00`
- A7 최신 기사 `GET /api/v1/articles?category=%00`

본문 칸도 같은 길로 DB 에 닿습니다(500 은 아직 미확인 — 시험을 먼저 써서 확인).
- A14 가입 `name` · `categoryCodes`
- A15 로그인 `loginId`
- A18 관심 분야 변경 `categoryCodes`

사용자 요청: 「A2 이슈 목록 · A6 사건 관련 기사의 category, A14 가입 name 에 NUL 이 들어오면 500 … 오늘 후속과 같은 방식으로 막자」. 단 A6 에는 `category` 인자가 없습니다. 실제로 500 이 나는 곳은 A2 · A7 입니다.

**원칙:** DB 에 묻기 전에 끊고, 지금 계약에 있는 답을 그대로 씁니다. 화면 쪽 약속(응답 · 오류 코드)은 바꾸지 않습니다.

| 어디 | NUL 이 들면 | 이유 |
|---|---|---|
| A2 · A7 `category` | 404 `CATEGORY_NOT_FOUND` | 계약이 「없는 코드 · 빈 문자열은 404」입니다. NUL 이 든 코드는 있을 수 없는 코드입니다 |
| A14 · A18 `categoryCodes` | 400 `VALIDATION_FAILED`, `errors[categoryCodes]` 「없는 관심 분야가 있어요」 | 없는 코드와 같은 답입니다 |
| A15 `loginId` | 401 `LOGIN_FAILED` | 가입 아이디 규칙(`[a-z0-9_]`) 때문에 NUL 이 든 아이디는 있을 수 없습니다. 없는 아이디와 같은 답이고 실패 횟수도 셉니다 |
| A14 `name` | 400 `VALIDATION_FAILED`, `errors[name]` 「이름에 쓸 수 없는 글자가 들어 있어요」 | 오늘 `q` 와 같은 방식입니다. 이름은 저장되는 값이라 이유를 알려 줍니다 |

`password` 는 해시만 저장되고 원문이 SQL 에 가지 않아 그대로 둡니다. 아이디 · `sort` 는 이미 정규식이 막습니다.

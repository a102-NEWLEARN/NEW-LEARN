# 배포 태그 MR 이 대기 중인 다른 영역 태그를 지우지 않게 — 열린 MR 브랜치에서 이어 받기 (Jira S15P31A102-174)

## 무엇을 / 왜

`deploy/app` 하나를 backend · frontend 가 같이 쓴다. `infra/ci/deploy_mr.py` 는 이 브랜치를 늘 dev 위에 새로 덮어쓰므로, 뒤에 온 파이프라인이 먼저 대기하던 영역의 태그를 지운다.

11-05 재현: FE 머지로 !677 이 frontend `53cbbe56 → 9ddae09a` 였는데, backend 파이프라인(`13416d02`)이 덮어써 backend 만 남았다. 제목에도 backend 만 남아 아무도 모른 채 09:44 에 머지됐고, 지금 사이트 frontend 는 `53cbbe56` 이다.

덮어쓸 때 열린 MR 브랜치에서 아직 dev 에 안 들어간 태그를 이어 받고, 제목 · 본문에 바뀌는 영역을 모두 적는다.

## 정할 규칙

영역마다 태그 후보가 셋이다. dev 의 태그, 열린 MR 브랜치의 태그(대기), 이 파이프라인이 구운 태그.

| 경우 | 결과 |
|---|---|
| 열린 MR 이 없다(머지됨 · 닫힘) | 대기 없음 — 지금처럼 dev 에서 새로. **닫은 MR 의 태그는 잇지 않는다**(사람이 버린 것) |
| 대기 태그가 dev 와 같거나 dev 가 더 새것 | 대기 버림 |
| 대기 태그가 dev 보다 새것 · 이번에 안 구운 영역 | 대기 유지(이어 받음) |
| 이번에 구웠지만 dev 가 같거나 더 새것 | 구운 태그는 안 넣는다(지금 규칙 그대로) |
| 이번에 구웠고 dev 보다 새것, 대기가 없거나 대기보다 새것 | 구운 태그 |
| 이번에 구웠고 dev 보다 새것, 대기가 같거나 더 새것 | 대기 유지 — 늦게 끝난 옛 파이프라인이 대기 태그를 덮지 않게(지금은 dev 하고만 비교해 덮는다) |
| 대기 태그를 읽을 수 없다(dev 나 브랜치 파일에 그 이미지가 없다) | 대기 없음 — 파일에 안 쓰이는 태그가 제목에 오르지 않게 |
| 이번에 구운 것이 하나도 새로 안 들어간다 | 커밋하지 않는다(잡을 다시 돌려도 브랜치 그대로). 열린 MR 제목이 계산한 제목과 다를 때만 제목 · 본문을 고친다 — 앞선 잡이 커밋 뒤 MR 갱신에서 죽었으면 다시 돌려 바로잡게 |

비교를 못 할 때(`merge_base` 가 200 이 아니다, 없는 커밋이면 400)는 `is_newer_or_same` 의 지금 규칙 「새 쪽으로 본다」를 그대로 쓴다. 그래서 대기 판정은 `not is_newer_or_same(dev 태그, 대기 태그)` 방향으로 부른다. 비교를 못 하면 대기를 유지하고 경고를 찍는다. 구운 태그와 대기 태그를 비교 못 하면 구운 쪽이 이긴다. 조용히 사라지는 쪽이 이번에 고칠 버그라 유지 쪽을 고른다.

## 바꿀 파일

- `infra/ci/deploy_mr.py`
  - `is_newer_or_same` — 끝 비교를 `== new_full` 에서 `.startswith(new)` 로. **고치지 않으면 재사용이 조용히 틀린다**: `merge_base` 는 전체 번호로 답하는데(11-05 실제 API 로 확인, `53cbbe56` → `53cbbe569f20…`) 짧은 태그와 `==` 로 비교하면 늘 False 다. 대기 판정이 늘 「dev 가 새것 아님」이 되어 dev 보다 옛 태그까지 이어 받는다. 전체 번호를 넘기는 지금 호출은 뜻이 그대로다. 경고 문구는 두 호출에 다 맞게 「`new` 를 새것으로 본다」로
  - 파일 읽기 둘을 `read_file(path, ref)` 로 묶는다 — dev · 브랜치 둘 다 읽어야 해서. `ref` 는 인코딩(`deploy%2Fapp`, 실제 API 로 200 확인). 못 읽으면 지금처럼 `sys.exit`, 브랜치는 안 건드린다
  - `waiting_tags(group, on_dev, on_branch)` 새 함수 — 위 표의 대기 판정
  - `main` — 열린 MR 조회를 덮어쓰기 앞으로 옮기고, 그 영역 묶음의 모든 영역을 돌며 위 표대로 최종 태그를 정한다. `changes` 에는 이어 받은 영역도 넣어 커밋 메시지 · 제목 · 본문에 다 적힌다
  - MR 본문 — 이어 받은 줄에 「앞선 파이프라인에서 구움」 표시, 「구운 파이프라인」 → 「이번에 구운 파이프라인」, GHCR 문장은 「태그를 올린 파이프라인의 이 잡이 확인」으로(이어 받은 태그는 다시 재지 않는다 — 태그 지우는 정책이 없다, `stack.md` 6절), 리뷰 포인트에 「이 MR 의 영역은 같이 반영되고 Revert 도 같이」 · 「닫으면 이어 받지 않는다」
  - 머리 설명문 6 · 9줄을 새 동작으로
- `infra/ci/test_deploy_mr.py` — 아래 시험, GitLab API 는 `deploy_mr.request` 자리에 가짜를 넣는다(새 의존성 없음)

## 리스크

- **두 영역이 같이 나간다.** backend 만 올리려던 사람이 frontend 까지 머지하게 된다. 제목 · 본문에 둘 다 보이고, 빼려면 MR 을 닫는다(다음 굽기가 새로 연다). frontend 를 CSP 해시 뒤에 머지해야 하는 때(`infra/k8s/services/app/routes.yaml` 87줄)는 그 frontend 태그가 든 MR 전체를 기다려야 한다
- 사람이 머지하는 순간과 겹칠 수 있다. 열린 MR 을 읽고 커밋하기 전 몇 초 안에 머지되면 브랜치만 다시 생기고 MR 이 없다 — 잡을 다시 돌리면 연다. 조회를 앞으로 옮겨 틈이 조금 넓어지지만 API 몇 번 사이다
- 브랜치 파일을 못 읽으면 잡이 빨개진다(새 실패 경로). 브랜치는 그대로라 다시 돌리면 된다
- 비교를 못 하는 경우 옛 태그를 이어 받을 수 있다. 잡 로그 경고로만 알 수 있다 — 본문의 `옛 → 새` 는 짧은 번호라 순서가 안 보인다. 태그는 dev 에서 구운 커밋이고 dev 는 보호 브랜치라, 실제로는 대기가 dev 보다 뒤처진 드문 때에 일시 오류가 겹칠 때뿐이다

## 되돌리는 법

## 계획에서 바뀐 것 (reviewer 계획 리뷰 반영, 11-05)

- 표에 dev 비교를 넣음 — 글대로면 구운 태그가 dev 보다 옛것일 때 dev 를 되돌림. 「dev 가 같거나 더 새것이면 안 넣음」 행을 따로 둠
- 「새로 들어가는 것이 없으면 안 건드림」에 예외 — 커밋 뒤 MR 갱신에서 잡이 죽으면 재실행이 제목이 틀린 채 초록으로 끝나므로, 제목이 다르면 고침

- 시험 환경: `redirect_stdout`, 상수 · 토큰 고정. 「지금 모양 그대로」를 제목 · 커밋 메시지로 좁힘(본문은 바뀐다)
- 비교 실패의 한계를 바로잡음 — 본문으로는 순서가 안 보인다. 제3의 상태를 만들어 본문에 표시하자는 제안은 드문 경우라 안 받고 리스크에 적음
- 시험 더함: `deploy/ai` 혼자, 두 영역 같이 구움

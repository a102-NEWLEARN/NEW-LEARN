# PostgreSQL 백업 — 매일 관리 서버 · 매주 S3 · 되살리는 법

## 무엇을 / 왜

DB 는 워커(Lightsail) 디스크 한 곳에만 있고 백업이 없다(`SSOT.md` 6절 「저장소·백업」 · 8절 「PostgreSQL 백업을 서버 밖에 둘지」, `infra/server/README.md` 「백업(pg_dump)은 아직 없다」). 워커를 잃거나 잘못된 마이그레이션 · 손 실수가 나면 기사 · 분석 결과 · 회원을 되살릴 길이 없다. 지금은 8.5MB(표 15개, 카테고리 5행)라 부담 없이 시작할 수 있고, NewsData 로 실제 기사가 쌓이기 전에 갖춘다.

## 작업 순서

### A — 매일 백업 (MR 하나)
- [x] `infra/k8s/bootstrap/pg-backup-pv.yaml` — 정적 local PV `pg-backup-local`(경로 `/var/lib/newlearn/pg-backup`, 5Gi 표시, control-plane nodeAffinity, 라벨로 고름)
- [x] `infra/k8s/services/data/postgres-backup.yaml` — PVC(그 PV 를 selector 로) + CronJob `postgres-backup`(schedule `0 4 * * *`, `timeZone: Asia/Seoul`, concurrencyPolicy Forbid, 성공 · 실패 기록 3개씩, activeDeadlineSeconds, 비루트 999, 요청 cpu 50m · 메모리 64Mi · 상한 256Mi). 하는 일: `postgres.data.svc` 에 pg_dump → `.part` → `pg_restore --list` → `newlearn-YYYYMMDD-HHMM.dump` 로 이름 바꿈 → 7일 넘은 `newlearn-*.dump` 지움
- [x] 서버 — 관리 서버에 폴더(`install -d -m 0700 -o 999 -g 999`) · PV apply, 이 매니페스트를 `kubectl apply --dry-run=server` 로 미리 확인 (dev 머지 **전에** PV 를 둬야 PVC 가 바로 묶인다)
- [x] 문서 — `infra/server/README.md` 「DB 백업」 절: 폴더 · PV, 손으로 한 번 돌리기(`kubectl -n data create job --from=cronjob/postgres-backup …`), 확인 명령(파일 목록 · 최근 잡), PC 로 가져오기, 되살리는 법(아래 C). `SSOT.md` 6절 「저장소·백업」 줄을 정한 대로 고치고 8절 줄은 지움(정해짐)
- [x] MR → infra → dev, Argo CD 반영 뒤 손으로 한 번 돌려 확인 · 보관 시험 · 되살리기 연습(검증 절)

### C — 되살리는 법 (A 의 README 에 쓰고 A 에서 연습)
- **연습(아무 때나, 사이트 영향 없음)**: 새 DB `newlearn_restore_check` 를 만들고 → 관리 서버에서 `sudo cat <파일> | kubectl -n data exec -i postgres-0 -- pg_restore … -d newlearn_restore_check` → 표 수 · 표마다 행 수를 `newlearn` 과 비교 → 연습 DB 지움
- **사고 때**: ① 같은 방법으로 `newlearn_restored` 에 되살리고 행 수 확인 ② `postgres` DB 에서 `ALTER DATABASE newlearn WITH ALLOW_CONNECTIONS false` → 연결 끊기(`pg_terminate_backend`) → `newlearn` 을 `newlearn_broken_<날짜>` 로, `newlearn_restored` 를 `newlearn` 으로 이름 바꿈 ③ health · backend 로그 확인. 망가진 DB 는 지우지 않고 남김(지우는 것은 사람이 정함). Argo CD 를 건드리지 않아도 되고, backend 는 몇 초 오류 뒤 새 DB 로 다시 붙는다
- **S3 에서**: apply 키로 받아(`aws s3 cp … --profile newlearn-apply`) 관리 서버로 보낸 뒤 위와 같이
- 덤프 시각 뒤에 들어간 Flyway 마이그레이션은 되살린 DB 에 없다 — backend 를 다시 띄우면 그 마이그레이션이 다시 돈다(README 에 적음)

## 리스크
- **백업 파일에 회원 정보가 들어 있음** → 관리 서버 폴더 0700(사용자 999), S3 비공개 · 암호화, PC 로 가져온 파일은 저장소 · zoo_docs 밖에 두고 쓰고 나면 지움(README 에 적음)
- **PV 보다 PVC 가 먼저 오면 Pending** → dev 머지 전에 서버에 PV 를 둠. 순서가 어긋나도 PV 를 두는 순간 묶임
- **관리 서버 디스크**(지금 62%, 남은 11G) → 덤프는 지금 1MB 안팎, 7일 보관이라 작음. README 확인 명령에 `df -h` 를 같이
- **IAM 정책을 손으로 바꾸다 틀림** → 고객 관리형 정책이라 이전 판으로 되돌릴 수 있음. JSON 은 저장소 파일을 그대로 붙임
- **업로드 키가 샘** → 올리기만 되므로 읽기 · 지우기 불가, 콘솔에서 비활성화하면 끝
- **되살리기 이름 바꾸기 중 backend 오류 몇 초** → 사고 때만 쓰는 절차, 연습은 사이트에 영향 없음
- **이름 바꾸기 직전 backend 가 다시 붙음** → `ALLOW_CONNECTIONS false` 를 먼저 걸어 막음
- **`terraform destroy` 가 버킷 때문에 멈춤**(force_destroy 끔) → 의도한 동작. 발표 뒤 정리 순서에 「버킷 비우기」를 README 에

## 되돌리는 법
- A: MR Revert → Argo CD 가 CronJob · PVC 를 지움. PV 는 `kubectl delete pv pg-backup-local`, 폴더와 백업 파일은 남음(지우는 것은 사람)
- B: MR Revert → 주간 CronJob · 봉인 Secret 이 빠짐. 업로드 사용자는 콘솔에서 비활성화 · 삭제. 버킷은 Terraform 코드를 되돌린 뒤 apply — 🔴 버킷을 지우려면 안의 백업을 먼저 비워야 하고, 비운 백업은 되살릴 수 없음(사람이 정함)
- apply 정책: 콘솔에서 이전 판으로
- 🔴 되돌릴 수 없는 것: 설치 자체에는 없음(아무것도 지우지 않음). 되살리기 절차도 망가진 DB 를 남김. 지우는 일(연습 DB 제외)은 모두 사람이 정함

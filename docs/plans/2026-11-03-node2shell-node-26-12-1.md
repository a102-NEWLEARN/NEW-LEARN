# Node2Shell — CI 잡 · frontend 빌드 단계 Node 26.12.0 → 26.12.1 (Jira S15P31A102-158)

## 무엇을 / 왜

Node2Shell(CVE-2026-111497)은 Node.js 에 묶인 Brotli(압축 형식) 디코더의 스트리밍 처리 버그다. 공격자가 보낸 Brotli 데이터를 `node:zlib` 으로 풀면 메모리가 깨져 원격 코드 실행까지 갈 수 있다. 26 · 24 · 22.x 가 영향받고 보안 판은 26.12.1 · 24.22.1 · 22.23.4 다. CISA 의 KEV(실제 악용이 확인된 취약점 목록)에도 올랐다(출처는 Jira 158).

2026-11-03 점검에서 운영 사이트는 해당하지 않았다. 운영 컨테이너에 Node 가 없고 Brotli 를 푸는 곳도 없다. 남은 곳은 CI 잡 `w12:frontend` 와 `frontend/Dockerfile` 1단계(둘 다 Node 26.12.0), 그리고 화면 개발자 PC 의 안내 판(24.15 이상)이다. 위험은 낮지만 고치는 품이 적어 올린다.

## 계획에서 바뀐 것 (reviewer 조수 계획 리뷰 2026-11-03, 「고쳐야 함」 3 · 선택 반영)

- **배포 태그 MR:** 「frontend 만 머지」는 할 수 없다. 태그 MR 은 배포 설정 파일 단위라 `deploy/app`(backend + frontend)과 `deploy/ai` 두 개가 생긴다(`infra/ci/deploy_mr.py` 의 `AREAS`, `SSOT.md` 6절). 보안상 배포는 필요 없어 둘 다 닫아도 된다는 것으로 바꾸고, 작업 순서 칸으로 옮겼다
- **로컬 Node:** `docs/dev-environment.md` 49줄이 화면 개발자에게 「Node 24.15 이상」을 안내한다. 24.22.0 까지는 모두 영향받는 판이라 바꿀 파일에 넣었다
- **검증:** CI 잡 로그에 `node --version` 은 찍히지 않는다(`w12:frontend` 는 npm 명령만 돈다). 러너가 찍는 이미지 다이제스트와 레지스트리의 `NODE_VERSION` 으로 확인한다
- 파이프라인이 몇 번 도는지, 26.13.0 대신 26.12.1 을 고른 까닭, 되돌릴 때도 다시 구워진다는 것, 용어 풀이

## 바꿀 파일

- `.gitlab-ci.yml` 130줄 `w12:frontend` 이미지 — `node:26-trixie@sha256:1b84…cf7fe # Node 26.12.0` → `node:26.12.1-trixie@sha256:97fa0f1b59035c6072721a88d55be1371c7cb1cc942b521e1cc5c72ec87655f4 # Node 26.12.1`
- `frontend/Dockerfile` 5 · 6줄 — 같은 이미지와 주석의 판 번호
- `docs/dev-environment.md` 49줄 화면 — 「Node 24.15 이상(도구들의 최소 버전)」 → 「Node 24.22.1 이상 또는 26.12.1 이상(Node2Shell 보안 판, Jira 158 — 도구들의 최소 버전은 24.15)」, 확인한 버전 칸의 컨테이너 판도 26.12.1 로
- 이 계획 파일

새 다이제스트는 `node:26.12.1-trixie` 의 목록 다이제스트(여러 CPU 판을 묶은 목록의 지문)다. Docker Hub 레지스트리 API 로 받았고, linux/amd64 이미지 설정의 `NODE_VERSION=26.12.1`(2026-10-28 생성)을 확인했다. 리뷰 조수도 따로 다시 확인했다.

지금 `26-trixie` 태그는 26.13.0 을 가리킨다. 패치 판만 올려 바뀌는 폭을 줄이려고 26.12.1 을 판까지 적은 태그로 고정한다.

## 안 바꿀 것

- 2단계 `nginx-unprivileged` · backend · ai Dockerfile — 해당하지 않음
- `compose.yaml` 의 `node:26-alpine` — 판을 고정하지 않은 태그라, 각자 `docker compose pull` 하면 고친 판을 받는다(11-04 바로잡음: 화면은 `full` 프로필 안이라 `docker compose --profile full pull` 이어야 받는다 — Jira 162). Jira 158 에 팀 안내(호스트 Node 판 올리기와 함께)
- `.claude/stack.md` §2 「Node 26」 — 주 판만 적혀 있어 그대로 맞다
- 옛 계획 문서(`docs/plans/2026-10-20-ci-pipeline.md` · `2026-10-21-image-build.md`)의 `node:26-trixie` — 그날 기록
- CI 130줄과 Dockerfile 6줄이 같은 이미지를 두 곳에 적는데 어긋나면 잡는 검사가 없다 — 이번 범위 밖

## 리스크

- `.gitlab-ci.yml` 이 바뀌어 MR 파이프라인이 네 영역(frontend · ai · infra · backend)과 캐시 없는 이미지 굽기 세 개를 돈다. 이 일은 MR 두 번(작업 → infra, infra → dev)과 dev push 한 번이라 그만큼 반복된다. 굽기는 워커 노드에서 돌고 ai 를 캐시 없이 구우면 680 ~ 1040초다(`SSOT.md` 10절)
- dev 머지 뒤 이미지 세 개가 모두 다시 구워지고 배포 태그 MR 두 개(`deploy/app`, `deploy/ai`)가 생긴다. 그사이 다른 backend · ai 코드가 dev 에 들어와 있으면, 그 MR 을 머지하는 순간 그 코드까지 사이트에 나간다
- 새 Node 판에서 frontend 빌드 · 시험이 깨질 수 있다 — 패치 판이라 작을 것으로 보지만, MR 파이프라인으로 확인한다

## 어떻게 검증하나

- MR 파이프라인 성공 — `w12:frontend`(npm ci · format · lint · test · build)와 이미지 굽기 시험, 나머지 영역도 초록
- `w12:frontend` 잡 로그 첫머리에 러너가 찍는 이미지 줄의 다이제스트가 `sha256:97fa0f1b…` 인지
- dev push 의 `w4:frontend` 잡이 성공하고, 그 잡 로그의 바탕 이미지가 `node:26.12.1-trixie@sha256:97fa…` 인지
- `docs/dev-environment.md` 49줄이 보안 판을 가리키는지

## 되돌리는 법

- infra → dev 머지 MR 을 revert 한다(세 파일 · 네 줄) — 되돌리는 MR 도 `.gitlab-ci.yml` 을 바꾸니 이미지 굽기 세 개와 태그 MR 두 개가 다시 생긴다. 분야 브랜치도 다시 맞춘다. 데이터 · 운영 설정 변경 없음

# /write — 읽히게 쓰기

> 아무리 내용이 좋아도 읽는 사람이 이해하지 못하면 좋은 글이 아니다.

이 규칙은 **Claude 가 내보내는 모든 글**에 적용된다 — 계획 · 스펙 초안 · MR 본문 ·
커밋 메시지 · 조사 보고 · 채팅 답변. **plan 모드가 만드는 계획 파일도 포함**이다.

---

## 1. 결론을 맨 앞에

묻는 말에 **첫 문장으로** 답한다. 배경·과정·근거는 그 뒤다.

| | |
|---|---|
| ❌ | "확인해 봤습니다. 설정 파일 마지막 줄이 기본값을 덮어쓰고, 그 줄은 아직… 따라서 반영되지 않았습니다." |
| ✅ | "**반영 안 됐습니다.** 기본값을 덮어쓰는 마지막 줄을 아직 아무도 안 고쳤어요." |

이 규칙은 글 전체의 첫 문장에 적용한다. 문단마다 굵은 결론을 달면 모든 문단이 같은 틀로 찍힌다.

## 2. 굵게는 한 문단에 하나

전부 굵으면 아무것도 안 굵다. **한 문단에서 가장 중요한 것 하나**만 굵게.

## 3. 한 문단은 세 줄 안쪽

네 줄이 넘으면 나눈다. 문단 사이는 비운다.

## 4. 전문 용어는 그 자리에서 풀어 쓴다

처음 나올 때 한 번. 각주로 미루지 않는다.

- ❌ "멱등키로 중복 요청을 막는다"
- ✅ "**멱등키**로 중복 요청을 막는다 — 같은 요청이 두 번 와도 한 번만 실행된다는 뜻이다"

용어를 아예 안 쓰는 것도 아니다. **용어와 쉬운 말을 같이** 둔다.

## 5. 코드 이름을 문장 한가운데 박지 않는다

- ❌ "`OrderValidatorTest` 가 금액만 보므로 수량 0 은 못 잡는다"
- ✅ "검증 테스트가 **금액만 봐서** 수량 0 은 빠진다 (`OrderValidatorTest`)"

경로·클래스 이름은 **문장 끝 괄호**나 표로 뺀다.

## 6. 층을 세 개까지만

제목 · 소제목 · 표 · 인용 · 목록을 한 화면에 다 쓰지 않는다.
**하나를 골라 끝까지 쓴다.** 표가 맞으면 표만, 목록이 맞으면 목록만.

## 7. 물어본 것에만 답한다

곁가지는 **맨 끝에 한 줄**로 몰거나, 선택지로 내놓고 고르게 한다.

## 8. 흐름과 갈래는 mermaid 로 그린다

읽는 사람이 머릿속에서 다시 그려야 하는 것 — **순서 · 분기 · 의존 · 상태 전이** — 은 그림이 맞다.
표는 그림이 아니다. **화살표가 있어야 흐름도다.**

| 무엇을 | 어떤 그림 |
|---|---|
| 순서가 있는 일 | `flowchart LR` |
| 갈래가 있는 판단 | `flowchart TD` |
| 두 쪽이 주고받는 것 | `sequenceDiagram` |
| 단계·상태가 바뀌는 것 | `stateDiagram-v2` |

`mermaid` 코드블록은 GitHub · GitLab 의 MR/PR 본문과 저장소 문서에서 그려진다.
터미널 채팅에는 원문이 그대로 보인다. **채팅에서는 그림 없이 짧은 목록으로 쓴다.**

🔴 **이미지 파일로 만들지 않는다** — 디프에서 안 보이고 다음 사람이 고칠 수 없다.

- **그림 하나에 개념 하나.** 노드가 여덟을 넘으면 두 장으로 나눈다
- **그려 놓고 같은 내용을 글로 또 쓰지 않는다.** 그림이 답이고, 글은 그림이 말 못 하는 것만
- 노드 이름에 `:` 이나 `·` 가 들어가면 큰따옴표로 감싼다. 안 그러면 파싱이 깨진다

## 9. 문장에서 기계 티를 걷어낸다

1~8 이 **글의 구조**를 다뤘으니 이 절은 **문장**을 본다. 구조가 맞아도 문장이 번역투면 안 읽힌다.

아래는 **커밋 · MR 본문 · 계획 · 보고에서 실제로 반복되는 것**만 골랐다. 전부 뜻을 안 바꾸고 고칠 수 있다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| **연결어미 뒤 쉼표** | 통과했지만**,** CI 는 빨갛게 떴고**,** 원인은 못 찾았다. | 통과했지만 CI 는 빨갛게 떴고 원인은 못 찾았다. |
| **「문제는 ~라는 점」** | **문제는** 캐시가 만료돼도 옛 값을 돌려준**다는 점입니다.** | 캐시가 만료돼도 옛 값을 돌려줍니다. |
| **문단마다 「따라서·이를 통해」** | 인덱스를 추가했습니다. **이를 통해** 응답이 줄었습니다. | 인덱스를 추가하니 응답이 줄었습니다. |
| **빈 동사** | fix: 중복 발송 방지를 통한 안정성 **개선** | fix: 알림이 두 번 가지 않게 |
| **「-성·-적·-화」 쌓기** | 누락 가능**성**에 대한 검증의 자동**화**가 필요합니다. | 응답에 필드가 빠지지 않는지 테스트로 검증해야 합니다. |
| **「이 변경은 ~을 제공」** | **이번 MR 은** 검증 로직을 **제공합니다.** | 업로드 파일 크기를 검증하는 코드를 넣었습니다. |
| **행위자 지운 피동** | 요청 로그는 미들웨어**에 의해 기록되고 있습니다.** | 미들웨어가 요청 로그를 남깁니다. |
| **have·make 직역** | 이 모듈은 순환 의존을 **가지고 있습니다.** | 이 모듈에 순환 의존이 있습니다. |
| **형식명사로 끝내기** | 빌드 캐시가 옛 의존성을 붙잡고 있**던 것이다.** | 빌드 캐시가 옛 의존성을 붙잡고 있었다. |
| **자기 변경 자화자찬** | 이번 변경은 **매우 중요한 의미를 가집니다.** | 이번 변경으로 로그인이 실패한 까닭이 화면에 뜹니다. |
| **「다만 한계도 분명」 문패** | 통과했습니다. **다만 한계도 분명합니다.** 동시 요청은 못 봤습니다. | 통과했습니다. 동시 요청은 확인하지 못했습니다. |
| **완곡 두 겹** | 회귀가 발생할 **가능성이 있을 것으로 보입니다.** | 회귀가 생길 수 있습니다. |
| **`-들` 남용** | 잡**들**이 슬롯**들**을 기다린다. | 잡이 슬롯을 기다린다. |
| **수를 명사 앞에** | 결함 **둘**을 찾았다 · 조건은 **넷**이다 | 결함 **두 개**를 찾았다 · 조건이 **네 가지**다 |

표로 안 되는 규칙 두 가지.

- **명사 앞에 수식을 3중으로 쌓지 않는다.** 핵심 명사에 닿기 전에 독자가 지친다. 문장을 끊는다.
  ❌ 「이미 결제된 주문을 다시 결제하는 요청을 막는 검증이 빠진 결제 API 를 고쳤습니다」
  ✅ 「결제 API 를 고쳤습니다. 이미 결제된 주문을 다시 결제하는 요청을 막는 검증이 빠져 있었습니다」
- **「A가 아니라 B」 를 한 글에 두세 번까지만.** 편해서 자꾸 쓰게 되는데 문단마다 나오면
  모든 문장이 같은 틀로 굴러간다. 한 번만 남기고 나머지는 평서문으로 푼다.

> 외부 윤문(문장 다듬기) 도구를 쓰면 **4 · 5 · 6 · 8절이 이긴다.** 도구가 병기 · 괄호를 줄이거나
> 표 · 목록을 산문으로 풀자고 해도 따르지 않는다.
>
> 짧은 글(커밋 · 계획 · MR 본문)에는 윤문 도구를 부르지 않는다. 위 표로 충분하고 호출 비용이 글보다 비싸다.
> 긴 조사 · 보고에 쓸 때는 보고서 형식으로 고정한다. 안 그러면 목록과 🔴 표지를 산문으로 녹여 6 · 8절을 깨뜨린다.
>
> 🔴 **개인정보 · 자격증명 · 실제 데이터가 든 글은 어떤 경우에도 외부 윤문에 넘기지 않는다.**

## 글 종류별 추가 규칙

### 커밋 메시지

제목 형식은 팀이 적은 선언이 진실이다. 적은 칸만 훅이 강제한다 (`.claude/stack.md` §3 · `.claude/hooks/commit-msg`).
여기서는 **본문**만 다룬다.

- 제목은 **무엇을 했는지**가 아니라 **무엇이 달라지는지**
- 본문 첫 줄에 **왜**. 증상이 있었으면 증상부터
- 함정을 발견했으면 **다음 사람이 안 밟게** 적는다 — 이 저장소의 커밋이 가진 제일 큰 값어치다

### MR 본문

양식은 저장소의 MR·PR 템플릿이 진실이다 (`.gitlab/merge_request_templates/` 또는
`.github/pull_request_template.md`). 어느 쪽을 쓰는지는 `.claude/stack.md` §7 에 적는다.

- 리뷰어가 **어디부터 볼지**를 먼저 적는다
- 안 한 것 · 못 한 것을 빈칸으로 두지 않는다. 없으면 "없음"
- 스스로 의심스러운 곳을 **먼저** 짚는다. 리뷰어가 찾게 두지 않는다

### 계획 (`/plan`)

다섯 칸(바꿀 파일 · 안 바꿀 것 · 리스크 · 검증 방법 · 되돌리는 법)은 `/plan` 2절이 정한다.
여기서는 **읽는 순서**만 — 리스크를 검증 방법 **앞에** 둔다. 무엇이 무서운지 알아야
검증이 왜 그 모양인지 이해된다.

🔴 **plan 모드가 만드는 계획 파일이 특히 잘 무너진다.** 승인 화면에서 한 번에 읽는 글인데
표를 네 개씩 쌓아 놓으면 스캔이 안 된다. **판단이 필요한 것을 앞에, 근거는 뒤에** 두고,
바뀌는 흐름이 있으면 8번대로 그림 한 장을 넣는다.

### 조사 · 상태 보고

- **그림으로 되는 것은 그림으로** (8절)
- 숫자는 **어떻게 쟀는지**와 같이. "테스트 통과"가 아니라 "N개 통과 (실행 출력 기준)"
- 안 재본 것을 잰 것처럼 쓰지 않는다

## 내보내기 전 마지막 확인

```
구조
□ 첫 문장이 답인가
□ 굵은 글씨가 문단마다 하나인가
□ 네 줄 넘는 문단이 있나
□ 처음 나온 용어를 풀어 썼나
□ 물어본 것보다 많이 답했나
□ 흐름·갈래를 글로만 설명하고 있나 (MR · 문서라면 mermaid 로)

문장 — 앞의 셋이 가장 잘 걸린다
□ 연결어미 뒤에 쉼표를 찍었나        (~했고, → ~했고)
□ 「문제는 ~라는 점입니다」 꼴이 있나
□ 문단이 「따라서 · 이를 통해」로 시작하나
□ 「개선 · 강화 · 구축」처럼 디프를 봐야 아는 동사를 썼나
□ 「~을 제공합니다 · ~에 의해 기록됩니다」 — 행위자가 빠졌나
□ 「A가 아니라 B」를 세 번 넘게 썼나
```

🔴 **길이를 줄이는 규칙이 아니다.** 길어도 읽히면 된다. 층을 줄이고 순서를 바꾸는 규칙이다.

# /plan — 계획 세우기

## 0. 먼저 plan mode 를 켠다

plan mode 에서는 **파일을 고칠 수 없다.** 조사하고 계획만 낸다.
이미 켜져 있으면 그대로 진행한다. 꺼져 있으면 `EnterPlanMode` 도구로 켠다 — 권한이 필요 없는 도구다.
다 쓴 계획은 `ExitPlanMode` 로 내서 사람의 승인을 받는다.

터미널에서는 이 스킬이 내장 `/plan` 을 대신한다. 그래서 `/plan` 을 쳐도 plan mode 가 저절로 켜지지는 않는다.
데스크톱 앱 · VS Code 에서는 `/plan` 이 내장 명령(plan mode 켜기)으로 갈 수 있다 — 스킬이 내장 명령을
대신하는 것은 로컬 터미널에서만 보장된다. 그렇게 plan mode 에 들어왔어도 이 스킬의 틀로 계획을 쓴다.

## 1. 조사한다

- `.claude/stack.md` §7 이 가리키는 문서부터 본다. 이 작업의 스펙이 「기능 스펙」에 있으면 성공 기준 번호(AC-1 …)를 가져온다.
- 파일을 많이 뒤져야 하면 **explorer 조수에게 맡긴다.** 직접 다 열지 않는다.
- 모르는 것이 있으면 **추측하지 말고 물어본다**(`.claude/HARNESS.md` 약속 2).

## 2. 이 틀로 쓴다 — 다섯 칸은 반드시 채운다

다섯 칸은 바꿀 파일 · 안 바꿀 것 · 리스크 · 어떻게 검증하나 · 되돌리는 법이다.
무엇을 / 왜는 두세 줄로 쓰고, 작업 순서는 커밋을 여러 번 나눌 일일 때만 쓴다.

```
## 무엇을 / 왜
(2~3줄)

## 바꿀 파일
- <경로> — 무엇을
- ...

## 작업 순서 (커밋을 여러 번 나눌 일일 때만)
- [ ] <한 커밋에 담을 일> — 무엇으로 확인하나
- [ ] ...

## 안 바꿀 것
- (손대지 않겠다고 약속하는 범위. 이게 없으면 작업이 번진다)

## 리스크
- (뭐가 깨질 수 있나. 없으면 "없음")

## 어떻게 검증하나
- (무엇을 보고 됐다고 판정할 것인가. 테스트 이름·확인할 화면·부를 API. 스펙이 있으면 성공 기준 번호마다)

## 되돌리는 법
- (잘못됐을 때. 🔴 되돌릴 수 없으면 그 사실을 먼저 말한다)
```

**다섯 칸 중 하나라도 "미정"이면 계획이 아니다.** 모르겠으면 그 항목을 조사하거나 물어본 뒤에 낸다.

## 3. 언제 필수인가

| 필수 | 생략 가능 |
|---|---|
| 파일 3개 이상 | 오타·문구 수정 |
| 데이터 구조 · 인증 · 권한 · 결제 · 배포 | 한 파일 안의 국소 수정 |
| 되돌리기 어려움 (삭제 · 마이그레이션 · 외부 전송) | 이미 승인받은 계획의 연속 |
| 처음 해보는 방식 | |

## 4. 승인받은 뒤

- **승인된 계획을 `.claude/stack.md` §7 「승인한 계획」 자리에 남긴다.** plan mode 의 계획 파일은 기본으로
  이 컴퓨터(`~/.claude/plans/`)에만 있어서 새 대화 · 팀원 · reviewer 가 못 본다. 설정의 `plansDirectory` 를
  그 자리로 해 두었으면 이미 거기 있다. 자리가 「MR 본문」이면 MR 을 열 때 붙인다. 자리가 비어 있으면 어디 둘지 묻는다.
- **계획대로만 한다.** 하다가 "이것도 고치면 좋겠다"가 보이면 적어두고 넘어간다.
- 작업 순서가 있으면 한 줄을 끝낼 때마다 계획 파일의 체크박스를 채운다.
- **계획이 틀렸다는 것이 드러나면 멈춘다.** 밀고 가지 말고 무엇이 달랐는지 말한 뒤 다시 승인받는다.
- 작업이 끝나면 `/verify`.

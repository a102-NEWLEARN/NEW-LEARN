# /evals — AI 기능 검증

> **이 스킬은 선택 모듈이다.** LLM 을 부르는 기능이 없으면 `/harness-init` 이 설정(`skillOverrides`)으로 끈다.

## 왜 필요한가

프롬프트는 코드와 다르다. **한 줄 고치면 다른 곳이 조용히 나빠진다.**
테스트가 초록이어도 출력 품질은 알 수 없다. 그래서 따로 재야 한다.

---

## 🔴 순서를 지킨다

```
1. 실제 출력을 눈으로 본다
2. 무엇이 문제인지 찾는다
3. 그것을 재는 지표를 정의한다
4. 그다음에 고친다
```

**지표를 먼저 만들고 데이터를 거기에 맞추지 않는다.** 순서를 뒤집으면
"측정은 되는데 아무 의미 없는 숫자"가 나온다. 그건 없느니만 못하다 — **틀린 확신을 준다.**

---

## 프롬프트·모델을 바꿀 때

평가 명령은 `.claude/stack.md` §3 의 `<영역>_EVAL`, 평가셋은 §9 「평가셋 위치」에서 읽는다. 비어 있으면 지어내지 말고 묻는다.

- [ ] 🔴 **돌리기 전에 몇 건을 몇 번 돌리고 대략 얼마가 드는지 말하고 확인받는다.** 모델 호출은 돈이 나간다
      (`.claude/docs/agent-safety.md` 2절). 한 번 허락받은 횟수를 넘겨 다시 돌릴 때도 묻는다
- [ ] 바꾸기 **전** 기준선을 잰다. 기준선 없이 바꾸면 좋아졌는지 알 수 없다
- [ ] 🔴 **한 번에 하나만 바꾼다.** 프롬프트와 모델을 같이 바꾸면 어느 쪽 효과인지 모른다
- [ ] 같은 입력으로 잰다. 입력이 다르면 비교가 아니다
- [ ] **여러 번 돌린다.** LLM 출력은 흔들린다. 한 번 좋았던 것은 근거가 아니다.
      k 번 중 한 번이라도 맞으면 되는 기능(pass@k)과 k 번 모두 맞아야 하는 기능(pass^k)을 구분해서 센다
- [ ] 품질만 보지 않는다 — **응답 시간 · 비용**도 같이 잰다
- [ ] 결과를 기록에 남긴다 (`.claude/stack.md` §7 의 EXPERIMENTS. 형식은 `.claude/docs/trackers.md`)

## 평가셋을 만들 때

- 실제로 틀린 출력 20~50건에서 시작한다. 지어낸 예제로 시작하면 실제 실패를 못 닮는다
- **두 묶음으로 나눈다.** 지금 못 하는 것을 재는 묶음(능력)과 지금 되는 것이 계속 되는지 보는 묶음(회귀).
  회귀 묶음은 CI 느린 층에서 돌려 기준 아래로 떨어지면 막을 수 있다 — 막을지는 팀이 정하고 `.claude/stack.md` §9 「회귀 묶음으로 막나」에 적는다
- 채점은 코드로 되는 것(정답 일치 · 형식 · 필드)부터 쓴다. LLM 에게 채점을 맡기면(심판) 사람이 매긴 점수와
  먼저 맞춰 보고 일치율을 기록한다. 맞춰 보지 않은 심판의 점수는 근거가 아니다
- 🔴 **실제 개인정보를 평가셋에 넣지 않는다.** 합성하거나 지운다. 평가셋은 저장소에 들어가고 외부 모델로 나간다

## 하지 말 것

- 🔴 **"눈으로 보니 좋아 보인다"로 바꾸지 않는다.** 규칙 하나를 더해 한 경우를 잡으려다
  다른 경우를 깨뜨리는 일이 흔하다. 그것도 **조용히** 깨진다.
- 🔴 **라벨의 뜻을 다른 질문에 갖다 쓰지 않는다.** 어떤 질문에 답하려고 만든 지표인지
  확인하지 않고 재사용하면 틀린 결론이 나온다.
- **평가셋을 저장소 밖(외부 SaaS UI)에서 편집하지 않는다.** 원본은 코드와 같이 둔다.
  런타임이 바깥에서 당겨 가면 검증 자체가 무력해진다.
- **운영 환경에서 외부 추적 도구를 켜지 않는다.** 사용자 데이터가 밖으로 나간다.

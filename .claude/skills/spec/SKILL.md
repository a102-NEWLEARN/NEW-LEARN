# /spec — 기능 설계서 쓰기

**코드보다 먼저 쓴다.** 무엇을 만들지 정하지 않은 채 짜기 시작하면, 나중에 나온 결과물이
"원래 원하던 것"인지 판정할 방법이 없다.

## 1. 기존 문서부터 읽는다

`.claude/stack.md` §7 의 단일 진실 문서들. **새 스펙이 기존 문서와 어긋나면 안 된다.**
어긋나는 것을 발견하면 어느 쪽이 맞는지 확인하고 진 쪽을 고친다.

## 2. 이 형식으로 쓴다

```
# <기능명>

상태: 초안 / 확정 (<날짜, 절대 표기>)
이슈: <이슈 키나 링크. 없으면 "없음">

## 목적
(한두 줄. 사용자가 무엇을 할 수 있게 되는가)

## 하지 않을 것
(범위 밖. 이 절이 없으면 기능이 끝없이 커진다)

## 진입점 · 닿는 곳
(화면 · API · CLI · 함수 중 해당하는 것. 바뀔 파일과 인터페이스 이름)

## 동작 · 상태 전이
(무엇을 하면 무엇이 되는가)

## 데이터
(어떤 것이 저장되나. 기존 데이터 구조와의 관계)

## 성공 기준 (인수 기준)
- AC-1 (**테스트로 확인 가능한 문장으로.** "잘 동작한다"는 기준이 아니다) — 확인: <테스트 이름 · 화면 · API>
- AC-2 ...
- AC-n (마지막 줄은 끝에서 끝까지 한 번 돌려 확인하는 절차. /verify 3단계가 이 줄을 짚는다)

## 상태별 동작
- 비었을 때 / 처리 중 / 실패 / 권한 없음 (해당 없으면 `해당 없음 — <이유>`)

## 엣지케이스
- (동시에 두 명이 하면 / 중간에 끊기면 / 값이 아주 크면)

## 가정
- (정하지 않고 가정으로 둔 것. 틀려도 결과가 크게 다르지 않을 때만 — `.claude/HARNESS.md` 약속 2. 없으면 "없음")
```

성공 기준 번호(AC-1 …)는 테스트 이름 · `/verify` 3단계 보고 · 커밋 · MR 이 같이 쓴다.
한 번 붙인 번호는 다시 매기지 않는다. 기준을 빼면 그 번호는 비워 둔다 — 번호가 밀리면 남이 적어 둔 참조가 엉뚱한 기준을 가리킨다.

둘 곳은 `.claude/stack.md` §7 의 「기능 스펙」이다. 정해진 곳이 없으면 묻는다. 새 파일을 마음대로 만들지 않는다.

## 3. 모르는 것은 추측하지 않는다

명세에 없거나 모순되는 것이 나오면 **AskUserQuestion 으로 물어본다.** 한 번에 몰아서, 답에 따라 많이 갈리는 것부터 묻는다.
답 없이 시간이 지나 저절로 넘어간 질문은 답이 아니다.

물어볼 수 없는 상황이면 `.claude/stack.md` §7 이 가리키는 미결 기록(OPEN)에 적는다.
그리고 그 항목에 **의존하지 않는 부분부터** 만든다(`.claude/docs/trackers.md`).

## 4. 사용자가 승인하면 확정이다

확정 전에 세 가지를 본다 — 성공 기준마다 번호와 확인 방법이 있다 · 「하지 않을 것」이 비어 있지 않다 ·
기대고 있는 OPEN 항목이 없다 (있으면 그것부터 묻는다).

승인받으면 맨 위 상태를 `확정 (<날짜>)` 로 바꾼다. 승인 사실이 채팅에만 남으면 다음 대화가 모른다.
그다음 `/plan` 으로 간다. 스펙은 파일로 남으니 `/plan` 은 새 대화에서 해도 된다.

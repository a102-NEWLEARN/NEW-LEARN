# 드리프트 가드 — 어긋남을 자동으로 잡기

**드리프트(drift)** = 같은 사실이 두 곳에 적혀 있다가 한쪽만 고쳐져 어긋나는 것.

## 원칙

**한 곳에만 적는다.** 어쩔 수 없이 두 곳이면 검사를 함께 만든다. 왜 한 곳에만 적나는 `HARNESS.md` 약속 4.

검사는 **CI 에 넣는다.** 사람이 기억해서 돌리는 검사는 결국 안 돌아간다.

---

## 패턴 1 — 자동 생성하고 커밋본과 비교한다

문서를 손으로 유지하지 않고 **코드에서 뽑아낸다.** 그리고 CI 에서 다시 뽑아
커밋된 것과 다르면 실패시킨다.

```
1. 빌드/테스트 중에 문서를 재생성한다
2. git diff --exit-code -- <문서경로>
3. 다르면 실패 → "재생성해서 커밋하라"
```

**쓰기 좋은 곳**: API 명세, 설정 목록, 명령어 도움말, 타입 정의.

> 이 패턴의 핵심은 **문서를 사람이 안 쓰는 것**이다. 사람이 쓰는 한 드리프트는 계속 생긴다.

---

## 패턴 2 — 두 설정 파일이 맞는지 테스트로 묶는다

계약이 **파일과 파일 사이**에 있을 때 쓴다.
예: 배포 설정의 헬스 주소 ↔ 앱 설정의 헬스 그룹 이름.
이 하네스에서는 `hooks/tests/test-deny-sync.sh` 가 시크릿 스캔의 비밀 파일 목록 ↔ `settings.json` deny 를 대조한다.

일반 테스트로는 못 잡는다 — 프로그램을 띄워도 배포 설정 파일은 안 읽히기 때문이다.
그래서 **테스트가 두 파일을 직접 열어서 대조**한다.

```
1. A 파일에서 값을 뽑는다
2. B 파일에 그 값이 정의돼 있는지 본다
3. 없으면 실패. 실패 메시지에 "어긋나면 무슨 일이 일어나는지"를 적는다
```

🔴 **이 테스트가 확인하지 못하는 것을 주석에 적어 둔다.** 안 적으면
다음 사람이 이 테스트가 전부 지켜 주는 줄 안다.

---

## 패턴 3 — 이미 적용된 것을 잠근다

한 번 적용된 뒤에는 **고치면 안 되는 파일**이 있다 (데이터 구조 변경 이력 등).
보통 체크섬으로 검증되므로, 고치면 **기동부터 실패한다.**

```
1. 적용된 파일 목록과 해시를 기록해 둔다
2. 테스트가 현재 해시와 비교한다
3. 달라지면 실패 → "새 파일로 바꿔라"
```

> **주석 한 글자만 고쳐도 터진다.** "내용은 안 바꿨으니 괜찮겠지"가 통하지 않는다.

---

## 패턴 4 — 잠금 파일(lock) 동기화

의존성 목록을 고치고 잠금 파일을 커밋 안 하면, 로컬과 CI 가 **다른 버전**을 쓰게 된다.

```
CI 에서 "잠금 파일을 갱신하지 않는" 모드로 설치한다
→ 목록과 잠금 파일이 어긋나면 그 자리에서 실패한다
```

---

## 패턴 5 — 문서에 적힌 수치를 테스트가 단언한다

문서에 성능·품질 숫자를 인용했다면, 그 숫자가 **어디서 나온 것인지** 코드로 붙들어 둔다.
안 그러면 어느 커밋에도 근거가 없는 숫자가 문서에 남는다.

---

## 패턴 6 — 코드로 둔 인프라와 실제 인프라를 대본다

누가 클라우드 콘솔에서 손으로 바꾸면 인프라 코드와 실제가 어긋난다. 다음 apply 가 그 변경을
말없이 되돌리거나, 코드를 믿고 한 판단이 틀린다.

```
주기적으로(하루 한 번 등) plan -detailed-exitcode 를 돌린다
→ 종료 코드 0 = 같다 · 2 = 어긋났다 · 1 = 실패
→ 2 면 알린다. 코드에 옮길지 실제를 되돌릴지는 사람이 정한다
```

읽기 권한만 가진 자격 증명으로 돌린다. 어긋남을 찾는 잡이 고칠 권한까지 가질 까닭이 없다.

---

## 가드를 만들 때 지킬 것

- **실패 메시지에 "어떻게 고치는지"를 쓴다.** 안 쓰면 사람들이 검사를 꺼버린다.
- **가드가 스스로 문서가 되게 한다** — 왜 이 검사가 있는지, 없으면 무슨 일이 나는지.
- **오탐이 잦은 가드는 없느니만 못하다.** 결국 무시하는 습관이 생기고,
  진짜 경고까지 같이 무시된다.
